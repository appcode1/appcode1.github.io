03

What is actually inside each APK

The difference is visible without running the apps: one package is mostly web assets, the other is mostly compiled native code.

qimen-webview — hybrid evidence

WebView
  • Entire front end is in assets/www/: index.html, CSS, page modules, and a 531 KB prebuilt dist/app.js.
  • Mini-program compatibility layer: runtime/runtime.js implements App, Page, getApp, and setData; runtime/wx-shim.js maps wx.* calls to browser APIs or the Kotlin bridge.
  • Local, offline loading: the manifest and code point to https://appassets.androidplatform.net/assets/www/index.html, served by AndroidX WebViewAssetLoader.
  • Custom bridge, not a standard framework: com.qimen.ganzhi.bridge.WebAppBridge exposes storage.save, storage.load, share.text, image.save, ui.setTitle, and similar methods.
  • No Compose, Room, or DataStore classes were found in the DEX. There is exactly one declared activity.
// assets/www/runtime/wx-shim.js
return JSON.parse(global.AndroidBridge.call(JSON.stringify({
  id: id,
  method: method,
  params: params || {}
})));

qimen-native — native evidence

Compose
  • No assets/www, no HTML/JS, and zero WebView references. The UI is rendered by Compose.
  • Native application class: com.qimen.app.QimenApplication, with com.qimen.app.MainActivity as the only activity.
  • Native persistence: com.qimen.app.data.db.QimenDatabase and SavedRecordEntity map to a Room table named saved_records; settings use DataStore’s preferences_pb.
  • Reference data is bundled, not scraped from web code: assets/reference/ contains the Qimen tables, lunar data, solar terms, 81 geju, and region data, each with a SHA-256 manifest.
  • Modern native libraries: Compose, Material3, Navigation Compose, Room, DataStore, kotlinx.serialization, and coroutines.

04

What this means in practice

Neither approach is inherently “better”; they optimize for different things.

qimen-webview · Hybrid

Portable, web-first trade-offs

Strengths

  • Reuses one HTML/CSS/JS codebase across platforms and is easy to update without rebuilding native screens.
  • The whole front end ships offline inside the APK; no remote server is required.
  • Fast iteration for UI and content changes.

Watch-outs

  • WebView startup and rendering overhead compared with native views.
  • Every native capability needs a JSON bridge method and error handling.
  • DOM-based UI may feel less native and needs extra accessibility work.
qimen-native · Native

Native performance, native cost

Strengths

  • Compose rendering, native lifecycle, and direct access to Android APIs.
  • Room and DataStore give structured, transactional local persistence.
  • Better fit for accessibility, large data views, and platform-consistent behavior.

Watch-outs

  • Requires a full native rewrite of UI and logic; no web code reuse.
  • More code to maintain per platform and a steeper Android-specific learning curve.
  • Larger DEX footprint, though the shipped APK is still compact.

Side-by-side installation: because the package IDs differ (com.qimen.ganzhi vs com.qimen.app), both APKs can be installed on the same device at the same time.
